# 校园闲置物品交换系统项目说明与五人分工

## 一、选题与应用场景

项目名称：校园闲置物品交换系统。

应用场景：学生在毕业季、换宿舍、社团活动、技能互助等场景中存在大量闲置物品和短期服务需求。系统提供"以物换物、技能换物、信用评价、安全面交"的校园内循环交换平台，减少浪费，提高闲置资源利用率。

创新意识：系统不是传统二手交易商城，不以现金买卖为核心，而是突出校园熟人半熟人场景下的低碳互换、技能服务互助、信用分约束和安全面交。

## 二、功能模块

1. 用户与权限模块：学生登录、管理员角色、个人资料、信用分。
2. 物品分类模块：数码设备、运动户外、生活用品、文创乐器、技能服务等分类。
3. 闲置发布模块：发布物品或技能服务，填写成色、地点、期望交换内容。
4. 检索浏览模块：关键词搜索、分类筛选、校区筛选、详情浏览。
5. 交换流程模块：发起申请、同意、拒绝、完成交换。
6. 站内消息模块：围绕交换申请进行留言沟通。
7. 收藏推荐模块：收藏物品，根据偏好和热度推荐。
8. 信用评价模块：交换完成后评价，影响用户信用分。
9. 举报审核模块：举报违规物品，管理员查看处理。
10. 运营看板模块：统计用户、物品、交换、热门分类、审计日志。

## 三、数据库表

系统设计 11 张核心表，满足不少于 8 张表要求：用户表、分类表、物品表、标签表、交换申请表、消息表、收藏表、举报表、评价表、通知表、审计日志表。SQL 文件位于 `database/schema.sql`。

## 四、技术方案

- 前端框架：Vue 3 + Vite + Pinia + Vue Router + Axios，响应式适配移动端。
- 后端技术：Go 1.21 + Gin 框架，RESTful API，JWT 认证。
- 数据存储：演示版使用 JSON 文件持久化，课程答辩可展示 SQL 表结构并扩展到 MySQL。
- 项目管理：Git 版本控制，按模块分支开发，合并前进行代码检查和功能自测。
- 协作方式：线上协作（微信群/腾讯会议），每人负责独立模块，接口文档提前约定。
- 软件质量保证：使用接口测试、页面流程测试、异常输入测试、移动端兼容测试。

## 五、五人小组分工（远程协作版）

### 分工原则

- 每人负责**完整独立的功能模块**（前端页面+对应后端接口），减少相互依赖
- 先统一接口文档和数据模型，之后各自并行开发
- 通过 Git 分支管理代码，每人在自己的分支开发，完成后提 PR 合并
- 每周一次线上会议同步进度，日常通过微信群沟通

### 为什么这样分

1. **模块独立**：每人负责的前端页面和后端接口是一一对应的完整功能闭环，开发时不需要等别人
2. **接口隔离**：只要提前约定好数据模型（model.go已定义），各模块之间通过 itemId/userId/exchangeId 关联，互不干扰
3. **并行度高**：5个人可以同时开发，不存在"等A写完B才能开始"的阻塞
4. **适合远程**：不需要频繁面对面讨论，各写各的模块，每周线上对齐一次即可
5. **贡献可量化**：Git提交记录清晰可查，每人有明确的代码文件归属

## 七、项目规模与管理分析

项目规模估算：
- Go后端代码：约 800 行（handler 500行 + service/middleware 300行）
- Vue前端代码：约 2000 行（10个页面 + 4个组件 + 路由/状态/API）
- SQL与文档：约 400 行
- 总代码量约 3200 行，功能点包括用户、物品、交换、消息、推荐、举报、评价、看板等，工作量不少于 TTMS 系统。

进度安排：

| 阶段 | 时间 | 任务 |
| --- | --- | --- |
| 需求分析 | 第 1 周 | 选题、竞品分析、用例建模、模块划分、接口文档 |
| 架构搭建 | 第 2 周 | A搭建骨架、D设计数据库、各成员熟悉代码结构 |
| 并行编码 | 第 2-3 周 | 各成员在自己分支开发负责的模块 |
| 联调测试 | 第 3-4 周 | 合并代码、联调修复、功能测试、移动端测试 |
| 文档答辩 | 第 4 周 | 整理报告、制作PPT、准备答辩 |

风险控制：

- 远程协作延迟风险：提前定义接口字段和数据模型，减少阻塞等待。
- 需求蔓延风险：优先完成核心交换闭环，再扩展推荐和看板。
- 成员失联风险：每周日晚强制线上同步，连续两天不回复群消息则A电话联系。
- 代码冲突风险：各人负责不同文件，基本不会冲突；公共文件修改需先群里知会。
- 答辩演示风险：准备本地可运行版本和录屏备份。
